# OTA client API

Mounted at `/ota-client/v1` for native clients. **Every call under `/app` is authorized by the version's
`API-KEY`** — the key stored on the `Version` being checked. No login session or Sanctum token is
required: a client holding the right key may check for updates and download the artifacts.

Requests also carry the `X-Device-Info` fingerprint, which registers and identifies the device. It is an
identifier, not a credential.

## Authentication

```http
API-KEY: <versions.api_key>
X-Device-Info: did=…;mf=…;br=…;mdl=…;av=…;sdv=…
```

- A missing or wrong key returns `401` (`{ success: false, errors: { api_key: … } }`) **before** the device
  is registered.
- The key is compared against the version the request resolves to: the bound `{version}` or `{bundle}` on a
  download, or the `package` + `version` named in the `/app/info` payload — falling back to the app's
  current version when that version is not listed, in which case only that current key is accepted.
- A key belongs to one version, so it cannot reach another app's artifacts.

## `GET /ota-client/v1/health`

Reachability probe — **public**, no key. The SDK resolves `false` instead of throwing when it is
unreachable.

## `POST /ota-client/v1/app/info`

```jsonc
// request
{
  "package": "com.example.app",
  "version": "1.3.0",
  "bundle": "1.3.0"
}
```

Response:

```jsonc
{
  "appId": "…", "versionId": "…", "bundleId": "…",
  "availableUpdates": {
    "version": { "id": "…", "name": "1.4.0", "updateType": "optional", "checksum": "…", "demo": false },  // a new APK
    "bundle":  { "id": "…", "name": "1.4.0", "updateType": "force", "demo": true }                       // a new JS bundle
  },
  "session": "…"                                  // optional, see below
}
```

If the reported `version` is not a version of the app — an old APK, or a build that was never published here —
the check still succeeds: the call is authorized with the app's current version key and
`availableUpdates.version` names that current version, instead of failing with `400 Invalid version`. The
reported `bundle` is only validated when the version is known (a registered bundle of it, or its
`default_bundle_version`), so an unknown build never fails on the bundle name embedded in its APK. `versionId`
is `null` in that case.

## Update type

Each offered update carries an `updateType` of `optional` or `force`, set per version and per bundle in
the dashboard:

- **`optional`** (default) — the client may show a "Not now" and let the user continue on the old build.
- **`force`** — the client must install it: the SDK hides the escape hatch, blocks the back gesture and
  refuses to dismiss the update.

Old clients ignore the extra field, and a client talking to an older server treats the update as
`optional`, so adding it is backward compatible.

## Demo releases

`demo: true` marks an offered update that is a [demo release](/guides/demo-releases). Demos are only
offered to a device linked to a user in an `allow_demo` domain bound to the app; when both a public and a
demo release exist, the newer one is offered. Downloading an unpromoted demo without that access returns
`404`. `checksum` is the APK's SHA-256, which the clients verify before installing.

## Downloads

```http
GET /ota-client/v1/app/update/version/{version}   API-KEY: <version.api_key>
GET /ota-client/v1/app/update/bundle/{bundle}     API-KEY: <version.api_key>
```

Both stream the stored artifact and record a download history row. The key must belong to the artifact's
version.

The APK download can also be opened by a **browser** (the SDK's "download new version" action hands the
URL to the OS). A browser cannot set the `API-KEY` header, so the key is accepted from the query as well:

```http
GET /ota-client/v1/app/update/version/{version}?api_key=<version.api_key>&did=<device id>
```

`api_key` is read only when the header is absent. Since it then travels in the URL (history, server
logs), prefer the header for the SDK's own requests.

## The returned `session`

`/app/info` still returns a `session` for SDK compatibility, but downloads no longer require it — the
`API-KEY` is the credential. Treat it as optional.

## Device registration

Devices self-register on first contact via the `X-Device-Info` header (`did`, `mf`, `br`, `mdl`, `av`,
`sdv`). The server creates or resolves the device after the key is accepted. `did` is client-supplied, so
it identifies a device rather than authenticating it.

## Device linking

A device receives demo releases only after it is linked to a user with a one-time code from the dashboard
(**Users → user → Demo access**, see [Users](/server-api/users#demo-access)). These routes use the same
`API-KEY` and device header as `/app`:

| Method | Path | Body |
|--------|------|------|
| `POST` | `/ota-client/v1/device/link` | `{ package, version, code }` — throttled to 10 per minute |
| `POST` | `/ota-client/v1/device/unlink` | `{ package, version }` |
| `POST` | `/ota-client/v1/device/info` | `{ package, version }` — the device's current link |

## Expo Updates protocol

Expo apps don't use `/app/info` for JS updates: their engine, `expo-updates`, speaks the [Expo Updates
protocol v1](https://docs.expo.dev/technical-specs/expo-updates-1/) to two routes:

```http
GET /ota-client/v1/expo/{package}/manifest   API-KEY: <version.api_key>
GET /ota-client/v1/expo/{package}/assets/{asset}?expires=…&signature=…
```

- **Manifest.** Requires `expo-protocol-version: 1` (else `406`), `expo-platform` and
  `expo-runtime-version`; the version is the one whose name equals the runtime version and whose client is
  `expo`. The answer is `multipart/mixed`: a manifest, or a `noUpdateAvailable` / `rollBackToEmbedded`
  directive. A device that must go back to an older bundle (withdrawn demo, lost access) first gets
  `rollBackToEmbedded`; its next check serves the older bundle.
- **Device.** Optional here. The app sends its id and device facts in `Expo-Extra-Params` (`did`, `mf`,
  `br`, `mdl`, `av`, `sdv`); without one, the device gets public updates only.
- **Assets.** The manifest lists temporary signed URLs (`OTA_EXPO_ASSET_URL_TTL`); the signature is the
  grant, so asset requests carry no key.
- **Signing.** With `OTA_EXPO_SIGNING_KEY` set, manifests are signed (`expo-signature`, RSA-SHA256) when the
  app asks for it.

The other routes (`/app/info` for new native builds, `/app/event`, `/device/*`, the APK download) work for
Expo apps as described above. For an Expo version, the reported bundle name is not validated.

## Client side

This contract is implemented by [`react-ota-client`](https://github.com/AbdoPrDZ/react-ota-client) and, for
Expo apps, by [`expo-ota-client`](/expo-sdk) on top of `expo-updates` — see [Client SDK](/client-sdk) and
[Expo SDK](/expo-sdk) for install and usage.
